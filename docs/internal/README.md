# Internal documentation

Use this directory for design proposals, implementation plans, migration
notes, experiments, and operational runbooks that are useful to maintainers but
are not promises made by the public documentation.

Internal documents should include:

- a date or status when the material is time-sensitive;
- the code paths or configuration they affect;
- explicit open questions and unresolved tradeoffs;
- a cleanup note when the document becomes obsolete.

Keep current behavior in the public pages under `docs/`; do not make readers
depend on an internal plan to understand the deployed system.
